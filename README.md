# Ceytom — Marine Electrical Storefront

Front-end prototype for **Ceytom Co L.L.C** (Dubai): a quote-driven storefront for marine
electrical switchgear, control and signalling components, aimed at commercial vessels.

Next.js 14 (App Router) · Tailwind CSS · mock data · no backend.

---

## Running it

```bash
npm install
npm run dev        # http://localhost:3000
```

```bash
npm run build && npm start   # production build (768 static pages)
```

No environment variables, no API keys, no network calls at build time.

## What this is built from

The catalogue is **not invented**. It is extracted from `HATCO_PRODUCT_CATALOG_2026`
(196 pages) and contains:

| | |
|---|---|
| Part numbers | **744** |
| Product photographs | **680** (91%) |
| Component families | 49, rolled into 8 groups |
| Manufacturers | 21 |
| Countries of origin | 7 |

Extraction scripts are in `tools/` (see below). `lib/catalog.json` is the generated output —
regenerate it rather than hand-editing.

### Why quote-only, with no prices

The source catalogue contains **no prices** — the "LIST 2026" column carries net weight only.
This resolves the open question in the Business Requirements Document: the storefront shows
*Price on request* throughout, and the RFQ basket is the single conversion path. There is no
add-to-cart and no checkout.

### Why the filters are what they are

The BRD was written around engine spares (IMPA/ISSA codes, engine-model fitment). This
catalogue is electrical control gear, where almost none of that applies. Filters are built on
the specifications that actually appear in the data and that a panel builder works from:

- Current rating (banded: ≤10 A, 10–25, 25–63, 63–125, >125)
- Voltage (12–48 V DC, 110–130 V, 220–240 V, ≥380 V)
- Ingress protection (IP20 → IP67)
- Mounting hole diameter (16 / 19 / 22 / 30 mm)
- Plate size (DIN cutouts: 48×48, 64×64, 88×88, 96×96, 72×72, 84×84, 48×96, 60×48)
- Pole count, contact arrangement, certification, manufacturer, origin, availability

Facet coverage is uneven by design — it reflects what the catalogue states. Empty fields are
hidden rather than shown blank. Coverage: certifications 97%, weight 95%, images 91%,
current 44%, voltage 37%, IP 26%, hole ø 22%, plate size 17%.

## Data files: what is real and what is synthetic

Everything in `lib/` is generated by a script in `tools/`. Regenerate rather than hand-editing.

| File | Source | Status |
|---|---|---|
| `lib/catalog.json` | `tools/extract.py` → `enrich.py` → `images.py` | **Real** — extracted from the printed catalogue |
| ↳ inventory fields | `tools/extend-catalog.js` | **Synthetic** — hash-seeded, deterministic |
| `lib/crossrefs.json` | `tools/build-crossrefs.js` | **Synthetic pairings, real series** — see below |
| `lib/assemblies.json` | `tools/build-assemblies.js` | **Inferred from real catalogue facets** |

```bash
node tools/extend-catalog.js     # inventory fields (idempotent)
node tools/build-crossrefs.js    # competitor cross-reference table
node tools/build-assemblies.js   # "what else does this need" graph
```

All three seed their pseudo-randomness from a hash of the product id, so the numbers are identical
on every machine and every reload. A demo where stock figures move between refreshes is worse than
no stock figures at all.

### Inventory fields (`tools/extend-catalog.js`)

The old free-text `stock` string ("In stock — Dubai") has been **removed**. It could not answer the
only question a buyer actually asks, which is *have you got twenty of them*. Availability is now
derived per query by `availability(product, qty)` in `lib/availability.js`.

| Field | Meaning |
|---|---|
| `stockQty` | Units on the shelf in Dubai. 0 for anything previously "Sourced to order" |
| `leadTimeDays` | Days to source, for zero-stock lines. `null` otherwise |
| `restockDays` | Days until a booked replenishment lands, for shallow stock. `null` otherwise |
| `moq` | Minimum order quantity — 5 / 10 / 25 on fuses, terminal blocks and bulbs; 1 elsewhere |
| `leadTime` | Kept, and kept in sync with `leadTimeDays` |

Distribution: 22.6% zero stock, 9.8% single digits, 45.8% at 10–39, 21.8% at 40+. The brief asked
for ~15% zero, but it also required every line previously marked "Sourced to order" to land on
zero, and that set is 168 of 744. The explicit rule wins; the remainder is split 55/20/10
renormalised.

States returned by `availability()`: `in-stock` · `low` (≤9) · `partial` (stock below the quantity
asked for) · `sourced`. The `tone` it returns names a **token family**, not a colour — `'accent'`
resolves through `--color-accent-ink`, which is the coral in the default palette and something else
in the other four.

### Cross-references (`lib/crossrefs.json`)

418 competitor references against 259 of the 744 listed parts — push buttons, e-stops, selector
switches, panel indicators, cam switches and relays, weighted the way enquiries actually arrive.

The competitor **series and part-number formats are real**: Schneider/Telemecanique XB4 · XB5 ·
XB6 · 9001K · K-series cam · RXM · RE22, Allen-Bradley 800F · 800T · 700-HN · 802T, Eaton/Moeller
RMQ-Titan M22 · DILM · ETR4 · LS, Siemens 3SU1 · 3SB3 · 3RT · 3LD2 · 3SE5, ABB CP1 · CL-502 ·
S200 · OT, Idec YW · HW · AL6, Omron A22 · A16 · MY · LY · MK · H3CR · E2E. An XB4-BA31 is a green
flush push button with one N/O contact, and it is pointed at a green flush push button with one
N/O contact.

**The individual pairings are generated, not verified.** A production table has to be built from
manufacturer data and signed off by sales. The `/cross-reference` page says so on the page, states
its own coverage (418 references / 259 of 744 parts), and prompts for anything not found rather
than implying the table is exhaustive.

Match types: `direct` (form, fit and function) · `functional` (works, with the difference stated in
a `note`) · `consult` (close, sales confirms). Notes are drawn from family-appropriate pools —
terminal orientation, mounting depth, housing material.

### Assemblies (`lib/assemblies.json`)

137 products carry relations; 49 of those are `requires`. Nothing here is a hand-invented pairing —
every relation is inferred from data already in the catalogue:

| Relation | Inferred from |
|---|---|
| Pilot lamp → bulb | The catalogue's own "w/o Bulb" wording; base type from cut-out, colour from the lens |
| Plug-in relay → base | Pin count parsed from the name, plus the sockets' own "Suitable for RFT1 …" text |
| Control device → guard / cover / box | Mounting hole diameter |
| Motor-duty cam switch → enclosure | Plate size |
| Panel ammeter → CT / phase selector | "CT Range" wording; selector matched on plate size |

Roles: `requires` (does not function without it — an error state, not an upsell) · `recommended` ·
`optional`.

**Contact blocks are a deliberate gap.** A 22 mm head needs one, and this catalogue does not list
contact blocks as separate lines. Rather than invent a part number, those relations carry
`unlisted: true` and an `x:` id; the UI adds them to a request as a free-text line for sales to
price. This is the honest answer and it is also the one that prevents the mistake.

| `/systems` · `/systems/[id]` | Six shipboard-location landing pages |
| `/brands` | Manufacturer table (cards on mobile) |

| `/policies/[slug]` | terms · shipping · returns · privacy (drafts) |

Header navigation carries six items; **Cross-reference is in the nav rather than only on the

other route to it from deep inside the catalogue. "By ship system" was shortened to "Ship systems"
so all six clear the theme switcher at 1024px — `audit.js` checks that width explicitly.

## Design tokens

Colours are **sampled from the logo pixels**, not eyeballed:

| Token | Hex | Use |
|---|---|---|
| `navy` | `#012731` | Dark surfaces, body text |
| `deep` | `#073D4A` | Secondary dark panels |
| `teal` | `#078F93` | Borders, fills, large display numbers |
| `tealink` | `#06787C` | Teal **text** on light backgrounds (4.5:1) |
| `coral` | `#EB6A4C` | CTA backgrounds — **paired with navy text** (5.01:1) |
| `coralink` | `#C94A2E` | Coral **text** on light backgrounds (4.66:1) |
| `mist` | `#E9EEF1` | Page background |
| `tint` | `#B7EEF1` | Highlights, text on navy |

Type: **Archivo Variable** (display) · **IBM Plex Sans** (body) · **IBM Plex Mono** (all part
numbers, specs and data). Self-hosted via `@fontsource` — no Google Fonts fetch.

Border radius is capped at 2px. No gradients. The only decorative element is a hairline
"wiring schematic" grid at 7% opacity on dark sections.

**Signature element:** every part number on the site is monospace and click-to-copy.

### Themes and the status vocabulary

Five palettes ship (Current · Deep Harbour · Chandlery · Tide & Teak · Switchboard), swapped by
`[data-theme]` on `<html>`. Every colour resolves through a CSS custom property, so nothing in the
markup is a literal. The registry is `lib/themes.js`; the palettes are `app/globals.css`.

The new features introduced three status ladders — availability, match type, sailing verdict — and
Switchboard is near-monochrome, so **hue is never the only carrier**. Each state pairs a token
colour with a glyph, a border weight and an explicit word, and the severity ramp reads in
greyscale: light outline → heavy outline → solid fill. Two rules in `components/Bits.jsx` keep it
working across all five:

1. **Coloured text states its own background.** `--color-accent-ink` reaches AA on the page
   background and only just — on a surface or a tinted wash it drops to ~4:1. Badges carry
   `bg-base` rather than inheriting whatever they were dropped onto.
2. **Availability labels are body-dark; the colour lives in the marker.** A label can land in a
   card, a banded panel or a warning box, so it cannot depend on its background. The marker is an
   8px shape with no contrast requirement, and its form differs per state anyway.

## Vessel-ETA, sharing and saving

**Vessel-ETA** (`lib/eta.js`). The request form's date field is a vessel-departure date, and every
line is scored against it: `ready = stock covers the quantity ? 0 : restockDays ?? leadTimeDays`,
then `arrival = ready + transit`. Transit comes from the delivery port — UAE 1 day, GCC 3,
international 7 — inferred from what the buyer typed and overridable with a selector. A line lands
on **makes it** with two or more days of slack, **tight** inside that, **will not make it** beyond
the date. Calendar days throughout, deliberately: working-day arithmetic would be marginally more
accurate and far harder to check by eye.

The working is always printed next to the verdict — *"14 of 20 in stock · balance of 6 in 10 days ·
3 days transit · on board day 13 of 18"* — because a superintendent will not accept a bare verdict.
Lines that miss offer a split shipment where stock covers part of the quantity, or a swap to an
in-stock part in the same family whose cut-out, plate size and voltage match. The same check is on
each product page in compact form.

**Sharing** (`lib/share.js`). The basket is base64url-encoded into the URL **hash**, not the query
string, so a vessel's parts list is never transmitted to a server, never lands in an access log and
never reaches an analytics tag. Opening a link with an empty basket restores silently; opening one
with items in the basket asks whether to merge or replace rather than overwriting. Past ~2000
characters a link stops surviving email clients, so the page says so plainly and offers a
`.json` file that re-imports.

**Saving.** "Save this list" names a basket into `localStorage`; `/quote/saved` restores, shares or
deletes them. The RFQ confirmation screen shows a reorder link for the request just sent, and
explains that in production it travels in the quotation email. Together this gives the client most
of what accounts were for — a standing list a vessel reorders each drydock — with no login, which
is what the BRD deferred.

## Verification performed

Audited with headless Chrome across nine routes:

- **Layout:** 1440px, 1024px and 390px — no horizontal overflow, no sub-11px text, no broken
  images, no console errors. 1024px is checked because the header carries six nav items, the theme
  switcher and the CTA on one row, and that is the narrowest width where they must all fit.
- **Contrast:** the sweep now runs **once per theme**, all five, and reports per theme. It seeds
  `localStorage` with the theme key and lets the site's own pre-paint script apply it — no test-only
  code path — and asserts the palette actually landed before measuring.
- **Build:** 768 static pages, clean compile.

Scripts: `audit.js` (layout) and `contrast.js` (contrast, compositing the real ancestor background
chain), sharing browser bootstrap in `browser.js`. Chrome is located via `CHROME_PATH` or the usual
install paths on Linux, macOS and Windows. Both need a server running:

```bash
npx next start -p 3307 &
node audit.js      # expect "No layout problems found."
node contrast.js   # per-theme pass/fail
```

### Current contrast state

**All five themes pass.** The only exemption is the *disabled* submit button, which WCAG 1.4.3
does not apply a minimum to. `contrast.js` matches it by text rather than by ratio, so a regression
on the enabled button is still reported.

Extending the sweep from one theme to five surfaced **623 failures the single-theme run had never
looked at**. All are fixed.

581 were fixed in markup, not in palettes: light-on-dark tiers raised from `/70`–`/80` to `/90`
(Tide & Teak's tint sits close enough to its primary that 70% missed AA), and `text-accent`
replaced with `text-accent-ink` on light backgrounds and `text-tint` on dark.

The remaining 42 were a single palette defect, pre-dating this work: **Deep Harbour's
`--color-text-on-accent` (`#07222B`) read 4.06:1 on `--color-accent` (`#1B8A9C`)**, against 4.5:1
required — which is every accent-filled button on the site, including the header CTA and
"Add to quote". Fixed by setting that one token to `0 0 0`, giving 5.16:1. No swatch, no theme
identity and no other palette value changed.

The lesson worth keeping: a contrast sweep that runs against whichever theme happens to be active
proves nothing about the others. If a sixth palette is ever added, `contrast.js` picks it up
automatically — it reads the registry out of `lib/themes.js` rather than keeping its own list.

## Before this goes live

**1. Replace the placeholder company details.** All in one object — `COMPANY` in
`lib/data.js`. Currently placeholders: TRN, trade licence, landline, WhatsApp, email,
street address.

**2. Legal review.** The four policy pages are drafts and carry a visible warning banner.
They must be reviewed by a UAE-qualified advisor. Nothing here is legal advice.

**3. Decide the class-approval position.** Catalogue certifications are industrial —
CE (680 lines), UL (354), TÜV (300), CSA (284), IEC (26), RoHS (10). There is exactly
**one ABS reference and no DNV or Lloyd's Register**. For newbuilds and class-surveyed
vessels, marine type approval is often mandatory. `/about` currently states this honestly
rather than implying blanket approval. Keep it that way, or substantiate specific lines.

**4. Confirm authorised-distributor claims.** `/brands` states distribution status is claimed
only where held in writing. Verify before publishing.

**5. Stock and lead times are synthetic.** `stockQty`, `leadTimeDays`, `restockDays` and `moq` in
`lib/catalog.json` are generated from a hash of the product id for demonstration. Wire these to
real inventory. The vessel-ETA feature is only as good as this data — it is the one thing that
must be live before the feature is put in front of a customer, because a wrong sailing-date
verdict is worse than no verdict.

**6. The RFQ form does not send.** `QuoteBuilder.submit()` mocks a reference number. Point it
at the sales inbox, and consider logging each request as a draft order for traceability —
email-only gives no visibility into quote-to-order conversion.

**7. The cross-reference table needs sales sign-off.** 418 generated pairings against real
competitor series. Every one has to be checked against manufacturer data before publication — a
wrong "direct" match puts the wrong part on a vessel. The page is honest about coverage today;
keep it that way as the table grows.

**8. The assembly graph needs an engineer's eye.** Inferred from cut-out diameter, plate size and
relay pin count. The inferences are conservative, but "requires" is a strong claim and should be
confirmed against manufacturer drawings.

**9. Decide whether to stock contact blocks as listed lines.** The catalogue lists 22 mm heads
but no contact blocks, so the site quotes them as free-text lines. Listing them would close the
single most common ordering mistake this catalogue permits.

## Regenerating the catalogue

```bash
cd tools
pip install pymupdf pillow --break-system-packages
python3 extract.py    # PDF → raw2.json  (positional parse)
python3 enrich.py     # raw2.json → catalog.json  (facets, groups, brands)
python3 images.py     # embedded images → public/products/*.webp + lib/catalog.json
cd ..
node tools/extend-catalog.js && node tools/build-crossrefs.js && node tools/build-assemblies.js
```

Run the three Node scripts in that order — the cross-reference and assembly builders read the
inventory fields the first one writes. `extend-catalog.js` is idempotent: on a fresh catalogue it
reads the `stock` string to recover the sourced-to-order set, and on a re-run it reads
`stockQty === 0` instead.

Two things made this non-trivial and are worth knowing if you re-run it:

- Section headers in the PDF are **letter-spaced** (`2 0 A  R o t a r y  C a m  S w i t c h`).
  They are recovered by detecting the yellow header bands from the PDF's drawing operators,
  then rejoining characters by measuring inter-character gaps.
- The weight column uses **spaces instead of decimal points** (`0 04` = 0.04 kg).

Images are trimmed of their white border, centred on a square canvas, capped at 520px and
converted to WebP (7.9 MB for all 680).
